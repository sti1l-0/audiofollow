# 音频跟随窗口所在屏幕 —— 技术方案与可行性评估

> 需求一句话：当某个应用的窗口位于屏幕 A 时，它的声音从扬声器 A 出；窗口拖到屏幕 B 后，声音自动改从扬声器 B 出。不改变系统默认设备。
>
> **v3 修订版**：本版基于 SoundSwitch 源码（`Belphemur/SoundSwitch` @ dev）的实测研究修订，删除原"音频会话检测"模块，修正了 5 处技术假设错误。**新增 §10 语言与运行时选型**——已用一份零依赖 Rust 探针实测证明"不用 .NET"路线可行。研究证据见《SoundSwitch源码研究笔记.md》，实测证据见《Rust方案实测报告.md》。

## 1. 需求拆解：从三个子问题收敛成两个

### ① 窗口 → 显示器（难度 ★☆☆☆☆）

| 步骤 | API |
|---|---|
| 枚举顶层窗口 | `EnumWindows` + `IsWindowVisible` |
| 窗口 → 进程 | `GetWindowThreadProcessId` |
| 取真实窗口矩形 | `DwmGetWindowAttribute(hwnd, DWMWA_EXTENDED_FRAME_BOUNDS, ...)`（比 `GetWindowRect` 准，能排除投影边框；最小化时返回 -32000，需过滤） |
| 判断落在哪个屏 | `EnumDisplayMonitors` 拿全部显示器矩形，与窗口矩形做**面积交集**，取最大者 |

**必须处理的坑：**
- **DPI 感知**：进程必须声明 `PER_MONITOR_AWARE_V2`（manifest 或 `SetProcessDpiAwarenessContext`）。否则在缩放不一致的多屏环境下，坐标是虚拟化过的，跨屏判断会错。
- **一个进程多个窗口**：浏览器、IDE、Office 都是。需要仲裁策略（见 §5）。
- **窗口横跨两屏**：按交集面积占比最大者归属；设阈值（如 >60%），否则保持不动，避免拖动中来回横跳。

### ② ~~识别"正在播声音的应用"~~ → **已删除**

> **修订说明**：根据你的意见，本模块删除。SoundSwitch 的实现证实这个模块**本来就不需要**——

它对音频的处理方式是：拿到窗口/进程的 PID，**直接**调 `SetPersistedDefaultAudioEndpoint`，完全不查询该进程当前是否在播放音频、也不枚举音频会话。搜索其 `SoundSwitch.Audio.Manager` 全部代码，音频会话 API（`IAudioSessionManager2`）**仅用于读取设备音量信息**，从未参与路由决策。

它的兜底策略是：**周期性扫描新进程**（`ProcessMonitor` 默认 2 秒一轮），新进程在下一轮才被上报（给进程启动留出初始化时间），再对规则命中的进程设一次路由。整个过程没有任何"是否在播放"的判断。

**所以你要的简化是成立的**，只需保留一个容错点（见下）。

### ③ 把应用改到指定设备（难度 ★★☆☆☆，修订）

接口链路已经在 SoundSwitch 里跑通并被大量用户使用：

```
AudioSes.dll!DllGetActivationFactory(L"Windows.Media.Internal.AudioPolicyConfig")
    → 取得激活工厂
    → IInspectable::GetIids() 运行时枚举出正确的 IID
    → QueryInterface → IAudioPolicyConfig
    → SetPersistedDefaultAudioEndpoint(pid, eRender, eRole, deviceId)
```

**五个关键技术细节（v1 全部写错或漏写，见 §9 对照表）：**

1. **用 `AudioSes.dll` 的 `DllGetActivationFactory`，不是 `RoGetActivationFactory`**。前者无需初始化 WinRT 运行时，从普通桌面进程直接调，更简单、依赖更少。
2. **IID 运行时发现，不硬编码**。先 `GetIids()` 拿到该工厂支持的全部 IID，取**列表最后一个**，再用 3 个已知 GUID 做白名单校验。这样微软改 IID 也自动适配，不需要试错。
3. **vtable 直接按字节偏移取**，不需要声明那一堆用不到的空方法桩：
   - `Set` → 偏移 `25 × 指针大小`
   - `Get` → 偏移 `26 × 指针大小`
   - `ClearAll` → 偏移 `27 × 指针大小`
4. **设备 ID 必须包成 SWD 设备接口路径**，不能直接传 `IMMDevice::GetId()` 的原始值：
   ```
   \\?\SWD#MMDEVAPI#{0.0.0.00000000}.{GUID}#{e6327cad-dcec-4949-ae8a-991e976a79d2}
    \__________/ \________/  \___________________/  \______________________________/
       固定前缀    设备实例ID          端点 GUID            渲染设备接口类 GUID
   ```
   读回时返回的也是这个格式，需要反向剥离。
5. **`PROCESS_NO_AUDIO`（`0x80070057` = `E_INVALIDARG`）是"静默失败"**，必须单独识别并容错：

> ⚠️ **这是"跳过音频检测"这个简化唯一的代价。**
> 该接口要求目标 PID **存在音频会话**，否则返回 `PROCESS_NO_AUDIO`，且**什么都不写**。
> 一个刚启动、还没播过任何声音的应用就没有会话 → 这次调用是空操作。
>
> **好消息**：SoundSwitch 用"2 秒轮询 + 延迟一轮上报"天然规避了大部分情况（进程起来后隔 2 秒再处理，此时音频通常已初始化）。我们照抄这个节奏即可。
> **兜底**：把 `PROCESS_NO_AUDIO` 当作"稍后重试"而不是错误，在下一次窗口移动/轮询时自然重试，或在检测到音频会话创建时补一次。**不需要为此专门建一个"谁在播声音"的模块**。

**权限**：不需要管理员（SoundSwitch 是普通托盘应用，直接在用户态跑）。注意别和 `IPolicyConfig::SetDefaultEndpoint` 搞混——那个是改**系统默认设备**，常需要管理员，我们**完全用不到**。

**持久化语义**：写入后**会出现在 Windows 音量合成器 UI 里，重启后依然存在**。必须：首次运行 dump 现有映射存档 → 提供"退出时还原" → 提供一键重置（`ClearAllPersistedApplicationDefaultEndpoints`）。

### 触发机制：双通道（照抄 SoundSwitch 的成熟设计）

SoundSwitch 用的是**事件 + 轮询**双通道，这个设计值得直接沿用，并替换触发条件：

| 通道 | SoundSwitch | **我们** |
|---|---|---|
| 事件通道 | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND / MINIMIZEEND)` → 前台窗口变了就套规则 | `EVENT_SYSTEM_MOVESIZEEND` + `EVENT_OBJECT_LOCATIONCHANGE`(节流) → **窗口位置变了就套规则** |
| 轮询通道 | `ProcessMonitor`，2 秒一轮，新进程延迟一轮上报 | **同上，原样复用**——顺便解决"应用重启后路由丢失"和"启动时路由未设"两个问题 |

> 轮询通道不是可选项。它同时解决三件事：① 应用重启后策略丢失；② 应用启动晚于窗口出现；③ WinEventHook 丢事件。SoundSwitch 用 2 秒、延迟一轮的节奏，实测有效。

### 去抖与差分（SoundSwitch 已有现成逻辑）

`SwitchProcessTo` 在写入前会**先读回全部角色的当前值**，全部匹配则直接返回，不写。这个差分判断必须保留——否则高频拖动会反复打断音频流造成爆音。

补充：拖动过程中**不做实际写入**，只在 `MOVESIZEEND` 落位时执行。

| # | 风险 | 影响 | 缓解方案 |
|---|---|---|---|
| 1 | **非公开 API 被微软改动** | 某次更新后失效 | **风险已显著降低**：运行时 IID 发现 + GUID 白名单校验，改 IID 能自动适配；仍可能有 vtable 偏移变化，故保留 `Unsupported` 降级路径并明确提示用户 |
| 2 | **~~GPL-3.0 许可证传染~~** | — | **已解除**：用户接受以 GPL-3.0 开源，可直接复用其代码与设计 |
| 3 | **粒度只能到应用级** | 同应用多窗口跨屏无法分开路由 | 产品上明说；多窗口时按面积占比最大者归属 |
| 4 | **`PROCESS_NO_AUDIO` 导致设置落空** | 应用尚未播过声音时设不上 | 容错为"稍后重试"；靠 2 秒轮询自然补上；不阻断流程 |
| 5 | **部分应用不即时生效** | 拖动后声音还从旧设备出 | 官方音量合成器同样如此；保留"重播提示"给用户 |

| 7 | **独占模式 / ASIO 应用** | 完全绕过系统路由 | 无解，跳过 |
| 8 | **持久化设置污染用户系统** | 音量合成器多出一堆映射 | 强制备份 + 退出还原 + 一键重置 |
| 9 | **高频切换造成爆音** | 反复写策略打断音频流 | 差分判断 + 落位才写 + 拖动中不写 |

| | **方案 A：per-app 端点重定向**（推荐） | 方案 B：虚拟声卡 + 用户态转发 | 方案 C：手动切换 |

## 5. 需要产品决策的点

1. **同一应用多窗口跨屏** → 建议按窗口面积占比最大者归属；两屏面积差 <20% 时保持不动。
2. **拖动中是否实时切换** → 建议只在 `MOVESIZEEND` 时切。
3. **是否支持"某应用钉死在某设备"白名单** → 建议要（SoundSwitch 的 `AppSoundRule` 就是这个思路，可参考其规则模型）。
4. **退出时行为** → 建议默认还原，设置项可改为"保持当前映射"。
5. **系统默认设备是否要动** → **绝对不动**。
6. **目标系统范围** → Win11 21H2+ 为主，兼容 Win10 1803+（SoundSwitch 用 `Build <= 16299` 做门控，低于 1709 直接降级）。

## 6. 分阶段实施计划（修订）

### Phase 0 — 验证 Spike（**半天**，v1 是 1～2 天）

风险已大幅降低，只需确认三件事：

1. 抄一份最简实现，对**正在播放**的 Chrome 设端点 → 看是否即时生效。
2. 对**没有播放**的应用（如刚打开的记事本）设端点 → 确认是否返回 `PROCESS_NO_AUDIO`。
3. **对 Chrome 传"窗口进程 PID"而非"renderer 子进程 PID"** → 确认是否生效。

> 第 3 点仍是唯一的真实未知项。SoundSwitch 用窗口 PID 且用户反馈其应用配置功能可用，所以大概率没问题；但这是必须亲手验一次的。
> **Go/No-Go**：若"播放中切换即时生效"在 Chrome / VLC / PotPlayer / foobar2000 上 4 中 3 成立 → 继续。

### Phase 1 — 改道层（**1 天**）

- 从零实现 COM interop（不复制 GPL 代码，见 §7）：激活工厂、运行时 IID 发现、vtable 偏移调用、SWD 设备路径、`PROCESS_NO_AUDIO` 容错、读回差分、降级实现
- 参考骨架已备好：`src/AudioFollow/Interop/AudioPolicyConfig.cs`

### Phase 2 — 屏幕判定（**1 天**）

- DPI 感知声明、显示器枚举、DWM 扩展边框、面积交集判定、多窗口仲裁
- 参考骨架已备好：`src/AudioFollow/Core/WindowScreenResolver.cs`

### Phase 3 — 触发闭环（**1～2 天**）

- WinEventHook（MOVESIZEEND 为主）+ 2 秒位置/进程轮询兜底
- 去抖、差分、`PROCESS_NO_AUDIO` 重试

### Phase 4 — 产品化（**3～4 天**）

## 10. 语言与运行时选型（实测结论：不用 .NET 也完全可行）

## 11. UI 与托盘选型

> 回答三个问题：① C# 做出来的 UI 够不够现代、动效够不够多；② Rust 走 Tauri 这类前端框架会不会更重、有没有别的问题；③ 注册到 Windows 托盘会不会成为选型障碍。
> 展开与实测数据见《UI与托盘选型.md》。

### 11.1 结论速览

| 问题 | 结论 |
|---|---|
| C# 做的 UI 够现代吗？ | **够**。.NET 9 起 WPF 内置**第一方 Fluent 主题**（明暗切换 + 系统强调色，`ThemeMode` 属性），不再需要第三方主题库；想要最"原生 Win11"的观感用 WinUI 3 |
| 动效多吗？ | **WPF**：XAML Storyboard + 硬件加速，能力足够但**大多要自己写**；**WinUI 3**：自带 Fluent 转场动画，开箱即用；**Web(Tauri)**：上限最高（CSS / WAAPI / Framer Motion） |
| Rust 走 Tauri 会更重吗？ | **比 Electron 轻一个量级，但比原生重一个量级**。而且 Tauri 依赖 WebView2 运行时——**和"不想用 .NET 运行时"是同一类顾虑**。注意：**Rust 做 UI 不必须用 Tauri**，iced / slint / egui 都是纯原生、零运行时 |
| 托盘会成为选型障碍吗？ | **不会**。三种实现都很简单；托盘真正的坑是共通的、**与语言无关** |

### 11.2 UI 框架对照（现代度 / 动效 / 开销）

| 方案 | 现代观感 | 动效 | 体积 | 运行开销 | 运行时依赖 |
|---|---|---|---|---|---|
| **WPF + 内置 Fluent 主题**（.NET 9+） | 良好 | 强（需自写） | 框架依赖 ~1 MB | 中 | .NET 桌面运行时（可自包含） |
| **WinUI 3**（Windows App SDK 1.8） | **最佳**（原生 Fluent/Mica） | **最佳（内置）** | 中 | 中高 | Windows App SDK 运行时 |
| **Rust + iced / slint** | 良好 | 中 | 单文件数 MB | **低** | **无** |
| **Rust + egui** | 一般（工具风） | 弱 | 单文件数 MB | **最低** | **无** |
| **Rust + 托盘基线**（实测） | — | — | **381 KB** | **11.3 MB 常驻 / 1 进程** | **无** |
| **Rust + Tauri 2（Web 前端）** | **最佳** | **最佳（Web 全套）** | 安装包数 MB | **中高（多进程 WebView）** | **WebView2 运行时** |

### 11.3 托盘：不是选型变量

三种实现都是几行到几十行的事：
- C#：`System.Windows.Forms.NotifyIcon`（WPF 项目打开 `UseWindowsForms`，或引用第三方 `NotifyIcon` 控件库）
- Rust：`tray-icon` crate（Tauri 官方团队维护）+ `muda` 菜单

**真正需要注意的是四条通用坑（与语言无关）：**

1. **新图标默认落进"溢出区"**（任务栏那个 `^` 里），需要用户手动拖出来。系统**没有**公开 API 能强制提升——`TrayNotify\IconStreams` 是**缓存语义**，系统会在更新/重启时按自己的策略重建，所以不要指望改注册表一劳永逸。
2. **`explorer.exe` 重启后图标会消失**：必须监听 `TaskbarCreated` 消息并重新 `Shell_NotifyIcon(NIM_ADD)`。成熟的 crate / 控件库通常已处理，自己写 Win32 时要记得。
3. **要"点图标弹出面板"（EarTrumpet 那种飞窗）**：用 `Shell_NotifyIconGetRect` 拿图标矩形，再据此定位一个 `WS_POPUP` 窗口；同时处理点击外部失焦自动关闭。
4. **多尺寸图标 + DPI 感知**：准备 16/20/24/32 多套尺寸；托盘线程必须有消息循环。

这四条在 C# 和 Rust 里完全一样，**不构成任何一方的优势或劣势**。

## 13. 原型落地与实测（本节取代 §12 中的旧结论）

> §12 里「基座选型已定：引用 `SoundSwitch.Audio.Manager` 当路由层」和「唯一剩余未知项是 Chrome 多进程 PID」两句**已经过时**。
> 实际走向：**Rust + slint 全自写，不引用 SoundSwitch**（GPL 传染性因此也不再是问题，本仓库以 MIT OR Apache-2.0 发布）。
> 写入路径、还原路径都已实测验证，不再是未知项。

代码在 `crates/af-core`（逻辑层）+ `crates/audiofollow`（托盘与界面），共 4 个提交。

### 13.1 语言与 UI 的最终选择

| 维度 | 结论 |
|---|---|
| 语言 | **Rust**。COM 互操作全部手写 FFI，除 `serde` 外无第三方库；核心改道层与 C# 版行数基本持平 |
| UI | **slint 1.18**，不是 Tauri。理由：本项目 UI 只有一屏，撑不起一条 Web 技术栈；slint 还省掉 WebView2 运行时依赖 |

### 13.2 实测数据（本机，Win11）

| 项目 | 实测结果 |
|---|---|
| IID 运行时发现 | `GetIids()` 返回 2 个接口 → 取到 `ab3d4648-e242-459f-b02f-541c70306324`，命中白名单 |
| 显示器枚举 | 2 块（2560×1440 @125% 主屏、1080×1920 竖屏 @125%），坐标与 DPI 均正确 |
| 音频端点 | 3 个（MON-A / MON-B / USB 扬声器），SWD 路径拼装正确 |
| 窗口归属 | 6 个顶层窗口全部正确落到所属屏 |
| **写入路径**（槽位 25） | 返回 `S_OK`，写后读回（槽位 26）与写入值**完全一致** |
| **还原路径** | 写空 HSTRING → `S_OK` → 读回变回「跟随系统默认」，**复检与改动前逐项一致，遗留影响：无** |

### 13.3 三个只有真跑起来才会暴露的问题

1. **写空字符串能恢复「跟随系统默认」。** 接口没提供"清除单个进程"的操作（槽位 27 是全局清除，会连别人的一起清掉），
   直觉上会认为写空值会被拒绝——SoundSwitch 里就有 `if (string.IsNullOrEmpty(deviceId)) return false;` 的保护，
   说明它的作者没试过。**实测：写空 HSTRING 返回 `S_OK`，读回变成"跟随系统默认"。**
   这条把原方案里"退出后会留下残余记录"这个最大缺陷直接消掉了。

2. **winit 与 COM 套间的冲突。** slint 的 Windows 后端是 winit，建窗时调 `OleInitialize`；
   而 `OleInitialize` 在"本线程已被初始化成 MTA"时会返回 `RPC_E_CHANGED_MODE`，winit 对此**直接 panic**。
   任何先做 MTA 初始化的 GUI 进程都会启动即崩。解法：GUI 进程自己先以 **STA** 初始化 COM，
   `OleInitialize` 随后拿到 `S_FALSE` 顺利通过。（Core Audio 在 STA 下完全可用。）

3. **tao 拒绝在主线程之外创建事件循环。** 托盘必须待在独立线程（主线程被 slint 占着），
   所以要显式声明 `EventLoopBuilderExtWindows::with_any_thread(true)`。

### 13.4 仍然成立的三条硬约束

1. **粒度只到「应用/进程」**，做不到「窗口」——同一 Chromium 的两个窗口跨屏只能按面积择大。
2. **目标进程必须已有音频会话**，否则写入返回 `PROCESS_NO_AUDIO` 被静默忽略，所以要重试。
   （触发方式已在 §14.2 升级为事件驱动 + 兜底轮询，但"必须先有会话"这条约束不变。）
3. **依赖未公开接口**，微软可能改坏它。IID 运行时发现 + 白名单校验能挡住大部分情况，但不是万无一失。

```bash

cargo run -p audiofollow -- --hook-test    # 事件钩子两级取证（合成事件 + 真实位移）
```

## 14. 第二轮迭代：显示器命名、多进程应用、实时触发

§13 把"能跑通"这件事解决了。这一轮解决三个**在真实使用中会让人直接放弃**的问题。

### 14.1 显示器型号取不到时退回「显示器 N」

**症状**：两块屏都显示 `Generic PnP Monitor`。信息量为零，用户根本没法把"哪块屏"和"哪个音箱"对上号。

**原因**：Windows 在拿不到 EDID 型号段时（虚拟显示驱动、某些转接线）会把这个占位串填进 `DeviceString`。
原实现的 `describe()` 遇到"看起来不可用"的名字时，会换一条路（`EDD_GET_DEVICE_INTERFACE_NAME`
拿 `\\?\DISPLAY#<型号>#...` 的第二段）再试一次，**但两条路都失败时它把占位串原样返回了**。

**修法**：

1. `describe()` 两条路都拿不到型号时返回**空串**，不再返回占位串；
2. 占位串判断从"包含 generic"扩成一张表（`Generic` / `Default` / `Non-PnP` / `通用` / `标准监视` / `即插即用监视器`），
   覆盖中英文两套本地化文案；
3. 展示层新增 `Monitor::display_name(ordinal)`：有型号用型号，没有就用「显示器 N」；
4. 配置文件里的 `monitor_name` 也存空串，展示时由 `monitor::name_from_device()` 从
   `\\.\DISPLAY2` 反推「显示器 2」——**纯字符串推导，显示器不在线时也能给出可读名字**；
5. 绑定列表按**当前实时扫到的显示器**解析编号（`ScreenRule::describe_in()`），
   这样列表里的「显示器 N」永远和上面的下拉框一致。

效果：

```
改前：显示器 1 · Generic PnP Monitor · 2560×1440     显示器 2 · Generic PnP Monitor · 1080×1920
改后：显示器 1 · 2560×1440 @125% · 主屏              显示器 2 · 1080×1920 @125%
```

（型号能取到的机器上仍显示型号，如 `显示器 1 · MON-A · 2560×1440`。）

> **§15 又往前走了一步，并且推翻了我在这里的判断。** 我当时以为"取不到型号"是硬件
> 或驱动不给，只能认命退回序数。实际上真型号一直躺在 EDID 里，读不到的原因是本项目
> 的 `DISPLAY_DEVICEW` 结构体声明**少了一个字段**——见 §15.1。现在序号只是兜底。

### 14.2 多进程应用：窗口 PID ≠ 音频 PID

这是 §12 里被标为"唯一剩余未知项"的那件事，也是这一轮工作量最大的一块。

**问题**：Chrome / Edge / Electron / WebView2 的窗口挂在主进程，音频在子进程（renderer 或
`--utility-sub-type=audio.mojom.AudioService`）。只按窗口 PID 写路由，这类应用**完全不生效**——
写的那个进程压根没有音频会话，写入还会被 `PROCESS_NO_AUDIO` 挡掉。

**方案**：`CreateToolhelp32Snapshot` 拍进程快照 → 建树 → 把窗口进程展开成
**「应用根 + 同名可执行文件的后代」**，逐个写。计划里因此区分两个概念：

- `PlannedRoute::pid` —— 应用根，做归属仲裁与展示；
- `PlannedRoute::targets` —— 真正写路由的进程集合。

#### 为什么后代必须限定「同名」

先用本机 296 个进程的真实数据做了对照，才敢定这条规则：

| 应用 | 后代总数 | 同名后代 | 异名后代 |
|---|---|---|---|
| `msedge.exe` (1836) | 19 | **19** | 0 |
| `msedgewebview2.exe` (11048) | 5 | **5** | 0 |
| `imapp.exe` (3544) | 15 | 4 | `imapp_helper`×10、`crashpad_handler`×1 |
| `launcher.exe` (8128) | 29 | 8 | `cmd`、`conhost`×9、`node`×3、`pwsh`、`sandbox-cli`×2 |

最后一行是否决"无脑展开全部后代"的关键反例：launcher 的子树里挂着 `cmd` / `node` / `pwsh`
——那是我自己这个会话启动的工具进程，和 launcher 毫无关系。展开它们就会把不相干的音频改道。
同理本机 `svchost.exe` 有 87 个实例，一旦某个 svchost 有了窗口，无脑展开会卷进大半个系统。

限定同名之后，浏览器系 100% 覆盖，启动器型零误伤。

#### 父 PID 复用必须校验

`PROCESSENTRY32W.th32ParentProcessID` 记录的是**当时**的父进程号。父进程退出后号码会被回收，
"父 pid"于是指向一个毫不相干的进程。照着这个假关系展开，会把路由写到别的程序头上。

识破办法：`GetProcessTimes` 比对创建时间，**父一定早于子**；若"父"比子还晚创建，这条边作废。
创建时间只在真正遍历到某条边时才惰性读取并缓存（几百个进程里我们关心的通常只有十几个），
问不到时间时**保留**这条边——宁可多认一个真父亲，也不要把正常的进程树剪断。

#### 同一应用的同名窗口会被折叠

若某个同名后代自己也有窗口（且在另一块屏上配了规则），它会被折叠进根，
按**总面积择大**归属——因为 Windows 层面一个进程只能有一条持久化路由，
"一个应用一条路由"是与平台能力一致的语义。发生取舍时计划会标注 `contested_monitors`。

#### 不覆盖的一类（如实说明，不假装）

宿主程序 + 独立的音频子进程，例如某 App 用 WebView2 播音频（声音出在 `msedgewebview2.exe` 里，
与宿主不同名）。计划会在「说明」里列出这类"正在出声但未被接管"的进程：

```
说明：app.exe、client.exe 正在出声但未被接管：
      与任何已改道的应用都不同名，也没有参与判定的窗口（本程序只按窗口归属改道）
```

这条说明按**可执行文件名**聚合、不带 pid——pid 每轮都在变，带上它这条说明每轮都不同，
上层的日志去重就失效了。

#### 附带解决：无效写入不再刷屏

一次同步会为每个目标进程产生一行结果。Edge 有 20 个目标，每轮就是 20 行。
两层处理：

1. **会话门控**：`reconcile` 拿到当前持有音频会话的进程集合，
   对**没有会话**的后代直接跳过——写进去也会被系统忽略，不如不调用；
2. **动作去重**：UI 层记住每个进程上一轮的动作，只在**动作发生变化**时打印。

### 14.3 事件钩子：从 1.5 秒轮询到 250 毫秒响应

**原状**：纯轮询，窗口拖到另一块屏后最多要等一个周期（默认 1500 ms）声音才换设备。
听觉上像是"坏了"。

**方案**：`SetWinEventHook` + 独立线程消息循环 + 去抖。

```text
钩子线程:  SetWinEventHook(0x8000..=0x800C, 0x0003..=0x0017, WINEVENT_OUTOFCONTEXT)
             └─ GetMessageW 循环（事件通过**安装钩子的那条线程**的消息队列派发）
主线程:    每 100 ms 醒一次 → 取事件计数 → 去抖 250 ms（上限 1 s）→ 同步
兜底:      每 4000 ms 无脑同步一次
```

关键设计决定：

| 决定 | 理由 |
|---|---|
| 钩子装在**独立线程**，不装在 slint/winit 的主循环上 | 免得把钩子的存活绑死在 winit 的消息泵实现细节上 |
| 回调里**只做一次原子加一**，什么都不干 | `EVENT_OBJECT_LOCATIONCHANGE` 在拖窗口时是**每帧**一条，回调里做重活会拖垮目标程序 |
| 用 `WINEVENT_OUTOFCONTEXT` 而非注入式 | 不做进程注入，不需要 DLL，也不需要管理员权限 |
| 保留兜底轮询 | 事件覆盖"用户摆窗口"，覆盖不了"进程重启后路由丢了"和"某个应用刚开始出声" |
| 去抖带 1 秒上限 | 有些窗口持续产生事件（动画、标题闪烁），没有上限就永远等不到"安静下来" |

#### 回调过滤条件与两个踩过的坑

`idObject != OBJID_WINDOW` 的事件必须全部滤掉。`idObject` 非 0 时事件主体是窗口内部的**部件**：
标题栏（-2）、客户区（-4）、鼠标指针（-9）、文本插入点（-8）——鼠标在窗口上一划就报一批，
频率极高且和"窗口在哪块屏"毫无关系。

坑一：**`OBJID_*` 常量是负数且从 -1 开始往下排，凭印象写必然错位。**
最初把 -2 写成 caret、-9 写成"窗口"，诊断输出反而误导人。加上环形缓冲把原始事件参数打出来之后，
一次就看清了真实取值。现在映射表按 `winuser.h` 实际取值写，并有单元测试钉住。

坑二：**自检的等待循环必须累加计数，不能"用条件表达式先读一次"。**
`take_events()` 是"取走并清零"语义，写成

```rust
// 错的：条件里这次调用已经把计数消费掉了，循环外再读必然是 0
while Instant::now() < deadline && hook.take_events() == 0 { sleep(); }
let n = hook.take_events();
```

会让钩子明明是好的、自检却报"收不到"。正确写法是把返回值累加。这个坑真实发生过一次，
而且**只有在真实窗口位移测试里才暴露**——合成事件那一路碰巧用了正确写法，掩盖了问题。

#### 两级取证

`--hook-test` 故意分两级，因为"钩子装上了"和"真实窗口移动能收到事件"是两件事：

| 级别 | 手段 | 本机结果（3 次一致） |
|---|---|---|
| ① 合成事件 | `NotifyWinEvent` 造一个事件 | ✅ 回调被调用且通过过滤 |
| ② 真实位移 | 把某窗口平移 2px 再复原（不激活、不改 z 序） | ✅ 收到 2 条事件，最近一条是 `EVENT_OBJECT_LOCATIONCHANGE` |

二级失败时会自动 dump 环形缓冲里的**原始**事件参数（含被滤掉的），把
`event / idObject / idChild` 摆出来，而不是让人猜。

### 14.4 验证结果

| 项目 | 结果 |
|---|---|
| 单元测试 | **38 个全通过**（协议/配置/命名/归属/进程树/计划/执行） |

## 15. 第三轮：显示器真名（EDID）与「同一应用多窗口」的最终答案

### 15.1 显示器名：从「取不到」到「MON-A / MON-B」

用户的要求很明确：**"我还是想要获取显示器名字，现在这个序数作为兜底。"**
上一轮只解决了"没名字时怎么显示"，没解决"为什么拿不到名字"。

于是把本机所有能取显示器名的路径全部跑了一遍，结果如下：

| 路径 | 给的东西 | 能当名字用吗 |
|---|---|---|
| `EnumDisplayDevicesW(dev, 0, ..., 0)` 的 `DeviceString` | `Generic PnP Monitor` | ✗ 占位串，两块屏完全一样 |
| 同一调用 + `EDD_GET_DEVICE_INTERFACE_NAME` 的 `DeviceID` | `\\?\DISPLAY#ACM2428#7&1a2b3c4d&0&UID0001#{e6f07b5f-…}` | △ 第二段 `ACM2428` 是硬件码，能区分但不直观 |
| 注册表 `Enum\DISPLAY\<hwid>\<inst>\Device Parameters\EDID` | EDID 二进制 | ★ **里面有型号名** |
| SetupAPI `SPDRP_FRIENDLY_NAME` | `Generic Monitor (MON-A)` | ○ 要抠括号，还要多一整套 SetupAPI 声明 |

**EDID 才是显示器的"自我介绍"**：它是显示器固件里的一段数据，型号名就在基础块第 4 个描述符
里（tag `0xFC`，13 字节 ASCII）。本机读出来是：

```
\\.\DISPLAY1  →  EDID 厂商码 ACM  →  型号名 MON-A     （2560×1440，主屏）
\\.\DISPLAY2  →  EDID 厂商码 ACN  →  型号名 MON-B       （1080×1920 竖屏）
```

正好和音频设备名里的型号一致（`MON-A (High Definition Audio)`、`MON-B (High Definition Audio)`），
用户可以直接把"哪块屏"和"哪个音箱"对上号——这正是要这个名字的目的。

#### 读取路径

```
MONITORINFOEXW::szDevice                            →  \\.\DISPLAY1
 └ EnumDisplayDevicesW(dev, 0, EDD_GET_DEVICE_INTERFACE_NAME)
     → DeviceID = \\?\DISPLAY#ACM2428#7&1a2b3c4d&0&UID0001#{接口 GUID}
                            ↑ 硬件ID   ↑ 实例ID
     └ 取中间两段 →
       HKLM\SYSTEM\CurrentControlSet\Enum\DISPLAY\ACM2428\7&1a2b3c4d&0&UID0001
        └ ...\Device Parameters\EDID       （REG_BINARY，本机 128 / 256 / 384 字节）
           └ 扫 0x36 / 0x48 / 0x5A / 0x6C 四个描述符槽，取 tag == 0xFC 的那条
```

只需要四个注册表 API（`RegOpenKeyExW` / `RegQueryValueExW` / `RegCloseKey`），
不引入 SetupAPI，依赖树仍然是零。四级回退：

**EDID 型号名 → 驱动填的 `DeviceString` → 接口路径里的硬件码（`ACM2428`）→ 「显示器 N」**

顺带还解析了 EDID 的厂商码（第 8-9 字节，3 个 5 位字母）：`ACM` / `ACN` / `ACO`。
它在型号名缺失时至少能告诉用户"这是哪家的屏"。

#### 真正的问题：`DISPLAY_DEVICEW` 少了一个字段

这是本轮最有价值的发现——**代码其实早就写好了，只是一直没生效**。

上一轮就已经实现了"读接口路径第二段"这条路，但本机从来走不到，白白退回序数。原因在 FFI 声明：

```c
typedef struct _DISPLAY_DEVICEW {
  DWORD cb;
  WCHAR DeviceName[32];
  WCHAR DeviceString[128];
  DWORD StateFlags;      /* ← 本项目的声明里漏了这个 */
  WCHAR DeviceID[128];
  WCHAR DeviceKey[128];
} DISPLAY_DEVICEW;
```

漏掉 4 字节 → `DeviceID` 整体**错位两个 UTF-16 码元** → 读到的头两个码元是
`StateFlags` 的低 16 位和高 16 位。`StateFlags` 的高 16 位是 0，
于是 `utf16_arr_to_string` 在**第二个码元**就遇到 NUL，返回一个 1 字符的垃圾串。

**它不崩溃、不报错、不返回失败**——只是 `DeviceID` 永远是空的，所有依赖它的路径静默失效。
这正是最容易骗过"读代码"的那类 bug：逻辑看起来完全正确，错在数据结构定义上。

修法：补上 `StateFlags`，并加编译期断言把总长度钉死：

```rust
// 4 + 64 + 256 + 4 + 256 + 256 = 840
const _: () = assert!(std::mem::size_of::<DISPLAY_DEVICEW>() == 840);
```

以后谁改动这个结构体，编译直接失败，不会再有"静默失效"。

> **定位手段值得记一笔**：本机是**另写了一份 Python ctypes 的等价探针**才找到的。
> Python 那边结构体抄对了，所以它能拿到 `ACM2428`，而 Rust 拿不到——两份独立实现互相印证，
> 比盯着同一份代码反复看有效得多。

### 15.2 同一应用多窗口：系统层面做不到（实测 + 根因）

用户问：**"Edge 多窗口这种情况，能解决吗？还是说是系统层面没办法给同一个应用的不同窗口设置音频。"**

答案是**后者**，但证据值得摆出来。设计的对照实验：开三个 Edge 窗口播放极低音量（增益 0.004、
55/65 Hz，基本听不见）的音频，两个窗口在**同一实例**（同 `--user-data-dir`），
一个在**独立实例**（不同 `--user-data-dir`），然后观察音频会话落在哪些进程。

| 实验组 | 进程结构 | 音频会话落点 |
|---|---|---|
| 同一实例 · **2 个窗口** | 该实例只有 **1 个** `--utility-sub-type=audio.mojom.AudioService` 进程 | 两个窗口的音频会话**都在这一个进程**里 |
| 独立实例 · 各 1 个窗口 | 每个实例各有 1 个 AudioService 进程 | 两个会话**分属不同进程** |

原始输出：

```
[同一实例] 浏览器根 pid=37312
   pid=30128  ★ AudioService      ← 两个窗口（55 Hz + 65 Hz）的音频都在这里
[独立实例] 浏览器根 pid=38444
   pid=34192  ★ AudioService

有音频会话的进程：
   30128  msedge.exe
   34192  msedge.exe
```

**两个窗口 → 一个进程 → 一条持久化记录 → 分不开。**

根因两层，都不是本程序能绕开的：

1. **系统接口粒度就是进程。** `SetPersistedDefaultAudioEndpoint(uint processId, EDataFlow flow, ERole role, IntPtr deviceId)`
   ——只有 pid，没有窗口或音频会话标识。交叉验证：EarTrumpet 的独立实现签名一致。
2. **Chromium 的 AudioService 是每个浏览器实例一个（单例）。** 与窗口数、标签页数无关。
   这是架构选择，不是配置问题——`--audio-process-per-tab` 之类的开关并不存在。

#### 三条绕法

| 方案 | 能做到什么 | 代价 |
|---|---|---|
| **多实例** | 用不同 `--user-data-dir` 开两个浏览器实例，就是两个进程组、两个 AudioService，可分别路由 | 要开两套窗口集；登录态需各自维护（可登同一账号靠同步） |
| **扩展 + `setSinkId()`** | Chromium 实现了 `HTMLMediaElement.setSinkId(deviceId)` 与 `AudioContext.setSinkId()`，扩展能对页面里的媒体元素**逐窗口**指定设备——**真正做到同一实例按窗口分流** | 要另写一个扩展；DRM 内容（Netflix 类）无效；网页自己调 `setSinkId` 会覆盖；扩展拿不到屏幕布局，需与本程序通过 Native Messaging 配合 |
| **不处理** | 按窗口面积择大（当前实现） | 同一浏览器的声音都落在同一块屏的设备上 |

> 第 1 条对**多进程应用**（Chrome / Edge / Electron）是唯一立即可用的办法；
> 第 2 条是唯一能真正做到"按窗口"的路，但要另开一条工程线。
> 当前实现走第 3 条，并在日志里明确写出"该进程在多块屏上都有窗口，已按面积择大"。

### 15.3 一个值得注意的观察：新进程可能自带持久化记录

实验里两个**全新启动**的 Edge 实例，其 AudioService 进程一建立音频会话，
读回就已经是「已固定到 `{0.0.0.00000000}.{964b0239-…}`」（= **MON-B**），而不是"跟随系统默认"。
而系统默认设备当时是 MON-A（`{0180224e-…}`），所以不是"自动记成系统默认"。

两种解释本次没有区分开：

- 该 PID 号此前被别的进程用过，记录被**继承**了下来（PID 复用）；
- 系统在应用首次建立音频会话时，**自动写入**了一条记录（值来自别处的历史状态）。

**对本程序的影响是可控的**：`reconcile` 永远是"先读原值备份 → 再写 → 退出时还原成原值"，
所以无论原值从哪来，都会被原样还回去，不会把别人的记录抹掉。
反过来说，这也解释了为什么"还原"必须**逐目标进程**做备份，而不能按应用名记账。
