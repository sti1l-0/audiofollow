# UI 与托盘选型 —— 三个问题的直接回答

> 回答的三个问题：
> ① .NET + C# 做 UI 确实容易，但做出来够现代吗？动效多不多？用户体验会不会更好？
> ② Rust 是不是得靠 Tauri 这类前端框架？会不会带来别的问题？前端开销是不是更大？
> ③ 不管用哪种后端语言，都要注册到 Windows 托盘，这里会不会有难点、会不会反而影响选型？

---

## 0. 三句话结论

1. **C# 的 UI 早就不"老土"了。** .NET 9 起 WPF 内置**第一方 Fluent 主题**（明暗切换 + 系统强调色）；想要最原生的 Win11 观感用 **WinUI 3**（Fluent + Mica + 内置转场动画）。动效上 WPF 能做但大多要自己写，WinUI 3 开箱即用。
2. **Tauri 既不是"更重"也不是"没代价"。** 它比 Electron 轻一个量级、比原生重一个量级。更值得注意的是：**Tauri 依赖 WebView2 运行时——这和你不想用 .NET 运行时其实是同一类顾虑**。而且对本项目这种 UI 体量来说，是拿重装备打小仗。
3. **托盘不影响选型。** 三种实现都很简单，真正的坑是共通的、**与语言无关**。

## 1. UI 现代度与动效能力：逐个说清楚

| 方案 | 现代观感 | 动效能力 | 要写多少代码 | 运行时依赖 |
|---|---|---|---|---|
| **WPF + .NET 9 内置 Fluent 主题** | 良好 | 强（Storyboard，硬件加速） | 中（动效多要手写） | .NET 桌面运行时（可自包含） |
| **WinUI 3**（Windows App SDK 1.8） | **最佳**（原生 Fluent / Mica / Acrylic） | **最佳（内置转场）** | **低** | Windows App SDK 运行时 |
| **WinForms** | 差（GDI+，2002 年的渲染） | 弱 | 低 | .NET 桌面运行时 |
| **Rust + iced** | 良好（wgpu GPU 渲染） | 中 | 中 | **无** |
| **Rust + slint** | 良好（声明式 DSL） | 中 | 中 | **无** |
| **Rust + egui** | 一般（工具/调试面板风） | 弱 | **低** | **无** |
| **Rust + Tauri 2（Web 前端）** | **最佳** | **最佳（CSS / WAAPI / Framer Motion）** | 中 | **WebView2 运行时** |

### 1.1 关于 WPF 的一个关键更新

过去说"WPF 显老"是对的——要现代观感得装第三方主题库（MaterialDesignInXaml、HandyControl、WPF-UI 之类）。

**但从 .NET 9 开始，WPF 有了第一方 Fluent 主题**：内置明暗模式切换、系统强调色跟随，通过 `ThemeMode` 属性控制。这是第一次不用第三方库就能做出 Win11 观感。

参照物：**EarTrumpet 本身就是 WPF**，观感并不差；它的问题从来不是"丑"，而是音频层被绑死在 app 项目里、以及必须走 MSIX 打包。

### 1.2 关于 Rust 侧的一个更正

**Rust 做桌面 UI 不必须用 Tauri。** 这是你的印象里比较容易被带偏的一点。Tauri 只是"用 Web 技术写界面"的那一条路，它的定位是**复杂富交互界面**（编辑器、画布、图表密集的应用）。

纯 Rust 还有：

- **iced** —— GPU（wgpu）渲染，Elm 架构，社区评价里最接近 Fluent 观感的一档
- **slint** —— 声明式 `.slint` DSL + 官方设计工具，可商用（开源版是 GPLv3，你已接受 GPL，不构成问题）
- **egui** —— 最轻最快，rust-analyzer 等工具在用，但风格偏"开发者工具"，现代感一般

这几条路都**没有任何运行时依赖**，单文件几 MB。

## 2. Tauri 的真实开销与隐性成本

### 2.1 公开基准（量级参考）

| 指标 | Electron | Tauri 2 |
|---|---|---|
| 安装包 | 80～150 MB | 2～12 MB |
| 空闲内存 | 150～300 MB（复杂应用可达 400 MB+） | 30～85 MB |
| 冷启动 | 1～3 s | 0.3～1.8 s |

**定位要准确：Tauri 是"比 Electron 轻一个量级"，不是"和原生一样轻"。** 它仍然是一个完整的 Chromium 系渲染引擎在跑，只是这个引擎不用你打包、由系统共享。

### 2.2 本机实测（2026-10-12）

| 项 | 实测值 |
|---|---|
| WebView2 运行时 | 已安装，版本 `154.0.4258.62` |
| 采样到的 `msedgewebview2` 进程组 | **6 个进程 / 394.2 MB** |
| 本机内存 | 32 GB（空闲 13.5 GB） |

⚠️ **这个数字要正确解读**：当前机器上跑的很可能是一个复杂 IDE 一类的重型宿主，不能直接等同于"一个轻量 Tauri 工具的开销"。但它揭示了一个**结构性问题**——WebView2 是**每个宿主一组多进程**（主进程 + GPU + 渲染 + 网络 + 若干 utility），所以它的开销不是"一个常数"，而是随界面复杂度增长，且**下限也不低**。

### 2.3 比"开销"更值得注意的隐性成本

1. **换了一种运行时依赖**。Tauri 在 Windows 必需 **WebView2 运行时**：
   - Win11：系统自带
   - Win10 1803+：通常随 Edge 存在
   - **LTSC / Server / 精简版：可能没有**，需要安装器引导用户下载（首次运行还要联网）
   - → 你最初"不喜欢 .NET 运行库"的动因（不想背一个运行时），在 Tauri 这里**以另一种形式回来了**
2. **两套语言 + IPC 边界**。UI 用 JS/TS，逻辑用 Rust，中间靠 `invoke` 通信。对我们这种"设置项改一下、读一下"的场景，等于每加一个功能都要跨一次语言边界。
3. **构建链更长**。Node + 前端 bundler + Rust 三段；改一行 UI 要过一遍前端流水线。
4. **权限模型要显式配置**，默认全关。
5. **调试跨栈**：前端问题开 DevTools，Rust 问题要挂原生调试器。

### 2.4 关键判断：我们的 UI 体量撑不起 Tauri

这个项目的 UI 实际复杂度：

| 界面 | 内容 |
|---|---|
| 托盘菜单 | 4～6 项（启用/暂停、打开设置、还原、退出） |
| 设置窗口 | 一张"显示器 ↔ 音频设备"映射表 + 几个开关（开机自启、退出还原、拖动即切） |
| 状态面板（可选） | 当前窗口/进程/目标设备的实时状态 |

**估计不到 800 行 UI 代码。** Tauri 的价值在复杂富交互，我们这里没有——用 Tauri 相当于为了一个设置表单引入一整条 Web 技术栈。

## 3. 托盘：真要小心的是这四条（与语言无关）

三种实现本身的难度：

| 方案 | 写法 | 难度 |
|---|---|---|
| C# | `System.Windows.Forms.NotifyIcon`（WPF 项目打开 `UseWindowsForms`，或引用第三方 `NotifyIcon` 控件库） | ★☆☆☆☆ |
| Rust | `tray-icon` crate（Tauri 官方团队维护）+ `muda` 菜单 | ★★☆☆☆ |
| 裸 Win32 | `Shell_NotifyIcon` 自己封装 | ★★★☆☆ |

**真正的坑是这四条，C# 和 Rust 完全一样：**

1. **新图标默认落进"溢出区"。** 任务栏上那个 `^` 里藏着，需要用户手动拖出来。系统**没有**公开 API 能强制提升到主任务栏。
   > 不要指望改注册表一劳永逸：`HKCU\...\TrayNotify` 下的 `IconStreams` / `PastIconsStream` 是**缓存语义**，不是持久配置。功能更新、累积更新、甚至 explorer 重启都可能触发重建，而重建后应用身份对不上，提升状态就丢了。正确做法是**把用户意图存在自己的配置里，在可预期的重置时机重新声明**。

2. **`explorer.exe` 重启后图标会消失。** 必须监听 `TaskbarCreated` 消息（`RegisterWindowMessage("TaskbarCreated")`）并重新 `Shell_NotifyIcon(NIM_ADD)`。成熟的 crate / 控件库通常已处理；自己写 Win32 时容易漏。

3. **想"点图标弹出面板"（EarTrumpet 那种飞窗）** —— 这是本产品很可能的交互形态，需要：
   - `Shell_NotifyIconGetRect` 拿图标的屏幕矩形
   - 据此定位一个 `WS_POPUP` 无边框窗口
   - 处理点击外部失焦自动关闭（`WM_ACTIVATE` / `WM_KILLFOCUS`）
   - 处理多屏 + 任务栏位置（上/下/左/右）+ 自动隐藏任务栏

4. **图标与 DPI。** 准备 16/20/24/32 多尺寸（或一个 ICO 多图层）；托盘所在的线程必须有消息循环，否则图标收不到回调。

**这四条在两种语言里是同一批 Win32 API，难度完全一样 → 托盘不构成选型依据。**

## 4. 实测：Rust 侧托盘的真实成本

跑了一个最小托盘原型（`src/rust-tray-spike/`，依赖只有 `tray-icon` 0.26 + `tao` 0.37），12 秒后自动退出：

```
=== AudioFollow tray spike ===
rss at start          : 8.2 MB
Shell_NotifyIcon      : OK (tray icon registered)
rss after tray created: 11.3 MB
rss at 4s (idle)      : 11.3 MB
rss at exit           : 11.3 MB
```

产物：`audiofollow-tray-spike.exe` = **390,656 字节（381 KB）**

里面包含：托盘图标（运行时生成的多色 RGBA 位图）、托盘菜单（含分隔符与禁用项）、完整消息循环。

### 4.1 开销三方对照

| | **我们的 Rust 托盘原型（本机实测）** | Tauri 2 空应用（公开基准） | WebView2 宿主（本机采样） |
|---|---|---|---|
| 二进制 | **381 KB** | 2～12 MB（含安装包） | — |
| 常驻内存 | **11.3 MB** | 30～85 MB | 6 进程 / **394 MB** |
| 进程数 | **1** | 2～5 | 6 |
| 运行时依赖 | **无** | WebView2 | WebView2 |

> 第三列是这台机器上一个复杂 IDE 类宿主的真实占用，**不能**当成"轻量 Tauri 工具的开销"。放在这里是为了说明 WebView2 的**结构性**特征：它是"每个宿主一组多进程"，开销随界面复杂度增长，而且下限也不低。

### 4.2 顺带验证到的两件事

1. **Rust 侧托盘没有任何额外门槛**：`Shell_NotifyIcon` 第一次调用就返回 OK，图标正常注册。第 3 节那四条通用坑（溢出区、`TaskbarCreated`、`Shell_NotifyIconGetRect`、多尺寸/DPI）在 Rust 里用同一批 Win32 API 处理，难度和 C# 一致。
2. **依赖极少**：整个托盘能力只来自两个 crate（`tray-icon` + `tao`），编译产物 381 KB，无外部运行时。

> 小提醒：这次原型会在你的任务栏上留下一条托盘图标记录（系统按 exe 路径记账）。图标本身在程序退出后就消失了，那条记录属于系统缓存，无害，Windows 会自行回收。

## 5. 建议

按你的关注点分流：

| 如果…… | 选 | 理由 |
|---|---|---|
| 最看重"省事 + 现代观感 + 动效够用"，能接受运行时 | **C# + WPF（.NET 9 内置 Fluent 主题）** | 一套语言、UI 白送、动效够用、生态成熟 |
| 要"最像 Win11 原生"的观感和开箱动效 | **C# + WinUI 3** | Fluent/Mica/转场动画全是内置的；代价是 Windows App SDK 运行时 |
| **坚持脱离 .NET**，且 UI 不复杂（我们的情况） | **Rust + iced 或 slint** | 无运行时、单文件几 MB、启动百毫秒级；动效要自己写但够用 |
| 想要 EarTrumpet 那种精细飞窗动效/数据图表 | **Rust + Tauri 2** | Web 动效上限确实最高；但要接受 WebView2 依赖 + 前后端两套语言 |
| 只是不想让用户装 .NET 运行时 | 保持 C#，开自包含发布 | 一行配置的事，不必换栈 |

**我的建议（针对这个项目）：Rust + iced/slint，而不是 Tauri。** 这个应用是"常驻托盘 + 偶尔打开设置"，UI 简单、启动要快、常驻内存要小——正是原生 GPU 框架的甜点区，而不是 Web 框架的。如果哪天你想要一个带动画的状态浮窗，再局部换 Tauri 也不迟（Rust 后端不用动）。
